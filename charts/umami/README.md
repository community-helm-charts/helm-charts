# Umami Helm Chart

This chart deploys [Umami](https://github.com/umami-software/umami), a
privacy-focused web analytics platform, using the official
`ghcr.io/umami-software/umami:3.4.1` image.

By default it creates one Umami Deployment, a ClusterIP Service on port 80,
an authentication Secret, and the repository's PostgreSQL subchart with an
8 Gi persistent volume. Umami itself stores its analytics in PostgreSQL and
does not need an application PVC. Ingress is disabled by default.

## Install from this repository

Requires Helm 3.7+ and Kubernetes 1.23+. Build the local dependencies before
installing:

```bash
helm dependency build ./charts/postgresql --skip-refresh
helm dependency build ./charts/umami --skip-refresh
helm install umami ./charts/umami --namespace analytics --create-namespace
kubectl port-forward --namespace analytics deployment/umami 3000:3000
```

Open http://localhost:3000. The initial login is `admin` / `umami`; change the
password immediately under Settings → Profile.

## Built-in PostgreSQL

The PostgreSQL username and database both default to `umami`. The password is
generated by the PostgreSQL subchart when not provided. Umami references that
same Secret, so both containers always use the same password.

For an externally managed PostgreSQL password:

```yaml
postgresql:
  auth:
    username: umami
    database: umami
    existingSecret: umami-postgresql-credentials
    existingSecretPasswordKey: password
  persistence:
    size: 20Gi
```

Create the referenced Secret in the release namespace before installing.
The password is a raw password, not a URL-encoded value. The chart encodes the
username, password, and database name into DATABASE_URL at container startup,
then runs the official image's startup script. The wrapper uses the image's
Node.js runtime and `exec` so the server receives termination signals.
`command` and `args` can override the application command after URL generation.

Other PostgreSQL settings are available under `postgresql`; see the
[PostgreSQL values](../postgresql/values.yaml). Service names, service ports,
and `global.postgresql` overrides are resolved from the subchart. If using
`namespaceOverride`, set `postgresql.namespaceOverride` to the same namespace
because the application must read the database password Secret there.

## External PostgreSQL

Disable the bundled database and provide a complete PostgreSQL connection URL.
Prefer an existing Secret in the release namespace:

```yaml
postgresql:
  enabled: false
database:
  existingSecret: umami-database
  secretKey: database-url
appSecret:
  existingSecret: umami-authentication
  key: app-secret
```

The database Secret must contain the full URL, for example
`postgresql://umami:URL_ENCODED_PASSWORD@postgres.example.com:5432/umami?sslmode=require`.
The database and user must already exist, and the user must be able to apply
Umami's schema migrations. External connection URLs are passed through unchanged;
encode reserved characters in the username, password, and database name.

Alternatively, set `database.url` in a private values file; the chart stores it
in a Kubernetes Secret:

```yaml
postgresql:
  enabled: false
database:
  url: postgresql://umami:password@postgres.example.com:5432/umami?sslmode=require
```

Use only one of `database.url` and `database.existingSecret`. Neither can be set
while the bundled database is enabled. MySQL is not supported by Umami 3.

## Authentication and upgrades

`appSecret.value` sets APP_SECRET. When empty, the chart generates a 64-character
secret and reuses it on upgrades through Helm's Secret lookup. For reproducible
offline rendering and GitOps, supply `appSecret.value` or `appSecret.existingSecret`
instead. Keep APP_SECRET stable and shared across replicas.

Changes to `appSecret.value` or `database.url` update a pod checksum and trigger
a rollout. Restart the Deployment after changing credentials in an externally
managed Secret. Changing a PostgreSQL password Secret does not change the
password stored in an existing database; coordinate password rotation with
PostgreSQL before restarting the application.

Umami checks its database and applies migrations on startup using the official
image's startup script. An unavailable database can cause startup retries until
PostgreSQL is ready. The startup probe allows time for migrations, and HTTP
probes use `/api/heartbeat`. Back up the database before upgrading. For upgrades
that require exclusive migration access, use `replicaCount: 1` and
`updateStrategy.type: Recreate` during the upgrade.

## Ingress and TLS

```yaml
ingress:
  enabled: true
  ingressClassName: nginx
  hostname: analytics.example.com
  tls: true
  annotations:
    cert-manager.io/cluster-issuer: letsencrypt
```

TLS references `analytics.example.com-tls`; provide the Secret or configure a
certificate controller. Additional hosts, paths, TLS entries, and rules follow
the repository's `ingress.extraHosts`, `extraPaths`, `extraTls`, and `extraRules`
conventions. Changing the Ingress path alone does not configure Umami for a
subdirectory; BASE_PATH requires a matching custom image build.

## Additional configuration

See [values.yaml](values.yaml) for image registry/digest overrides, replicas,
resource requests and limits, custom probes, scheduling, ServiceAccount settings,
sidecars, and extra volumes. The default application security context runs as
the official image's UID/GID 1001, drops Linux capabilities, and disables
ServiceAccount token mounting.

Pass additional [Umami environment variables](https://docs.umami.is/docs/environment-variables)
through `extraEnvVars`, `extraEnvVarsCM`, or `extraEnvVarsSecret`:

```yaml
extraEnvVars:
  - name: DISABLE_TELEMETRY
    value: "1"
  - name: CLIENT_IP_HEADER
    value: X-Forwarded-For
```

Use the dedicated values for PORT, HOSTNAME, DATABASE_URL, APP_SECRET, and
the internal UMAMI_DB_* variables; `extraEnvVars` rejects these names to avoid
conflicting configuration.
